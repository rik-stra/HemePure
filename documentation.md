# HemeLB Preprocessing and Boundary Condition Documentation

## Preprocessing Script: hemeLBpreprocSingle.py

### What the script actually does
The preprocessing script runs a two-pass voxelization workflow and then builds the files needed for a HemeLB run.

1. Writes an initial voxelizer XML with placeholder iolet points.
2. Runs voxelizer in ENDEARLY mode to discover all opening positions.
3. Matches user-provided inlet seed points to the nearest discovered openings.
4. Rewrites voxelizer XML with inlet openings first and outlet openings second.
5. Runs voxelizer to completion.
6. Converts voxelizer output to ROOTNAME.gmy.
7. Generates input_PP.xml from voxelizer iolet blocks.
8. Generates inlet and outlet weight files.
9. Removes temporary files.

### Command line interface

```bash
python3 hemeLBpreprocSingle.py STLFNAME STLUNITS INLETPOSITIONS_FILE NUMINLETS NUMOUTLETS DXreq NUMRANKS RANKSPERNODE tauDesired
```

The script requires exactly 9 user arguments.

### Parameters mapped to source behavior

| Parameter | Meaning in code | Notes |
|---|---|---|
| STLFNAME | STL file passed to voxelizer | ROOTNAME is derived from this file name |
| STLUNITS | Physical scale factor for STL coordinates | Used in voxelizer resolution ratio: DXreq/STLUNITS |
| INLETPOSITIONS_FILE | Path to a file containing inlet seed positions | The script reads only the first line |
| NUMINLETS | Number of inlets expected | Used to create placeholders and rename inlet weight files |
| NUMOUTLETS | Number of outlets expected | Used to create placeholders and rename outlet weight files |
| DXreq | Requested voxel size in physical units | Used directly as DX in generated XML and timestep formula |
| NUMRANKS | Parallel task count | Used in srun/mpirun/mpiexec launch string |
| RANKSPERNODE | Ranks per node | Used to compute nodes and cores per rank for srun |
| tauDesired | Relaxation time tau | Used to compute simulation step_length in input_PP.xml |

### Inlet and outlet position specification

This is the most important part.

#### 1) What you provide
You provide only inlet seed points, not outlet points.

The third argument is a file path. The script reads the first line of that file and parses it as:

```text
X1,Y1,Z1;X2,Y2,Z2;...;XN,YN,ZN
```

For example:

```text
0,0,0
```

or

```text
0,0,0;0.01,0.0,0.02
```

#### 2) Units and coordinate frame for inlet seed points
Inlet seed points are expected in physical coordinates consistent with DXreq and STLUNITS processing.

- Internally, each seed point is converted to lattice coordinates using:
  - lattice = physical / DXreq + SHIFTS
- SHIFTS comes from voxelizer output (ioletpositions.txt).

Practical rule:
- If your STL coordinates are in non-SI units, convert your seed points to physical units using the same scale logic implied by STLUNITS so they match the voxelized geometry in physical space.

#### 3) How inlet openings are selected
After ENDEARLY voxelization, the script gets all discovered iolet centers from ioletpositions.txt.

For each user seed point:
- Convert to lattice coordinates.
- Find the nearest discovered iolet center.
- Mark that iolet index as an inlet.

Safety check in source:
- If two user seed points map to the same nearest iolet, the script exits with an error.

#### 4) How outlets are selected
Outlets are not provided explicitly.

Any discovered iolet that is not selected as an inlet is treated as an outlet.

So outlet definition is implicit:
- outlets = all_openings - selected_inlets

#### 5) Ordering requirement used by voxelizer
The rewritten voxelizer XML always writes points in this order:
- First NUMINLETS points are inlets.
- Remaining points are outlets.

This ordering is how the downstream blocks and generated XML classify inlets vs outlets.

#### 6) Common failure modes
- INLETPOSITIONS_FILE contains more than one line: only line 1 is used.
- Seed points are far from intended openings: wrong inlet assignment.
- Two seeds near the same opening: script exits on duplicate nearest iolet.
- NUMINLETS/NUMOUTLETS do not match geometry openings: later steps can fail or produce incorrect file naming expectations.

## Generated input_PP.xml: fixed vs user-editable

The script writes input_PP.xml using write_heme_xml plus iolets_block_inputxml_PP.txt from voxelizer.

### Values written directly by script
- simulation/step_length is computed as:

```text
step_length = (tauDesired - 0.5) * DXreq^2 / (12e-6)
```

- simulation/steps is written as CHANGE (must be replaced before run).
- simulation/stresstype is 1.
- simulation/voxel_size is DXreq.
- simulation/origin is (0.0,0.0,0.0).
- geometry/datafile path is ROOTNAME.gmy.
- initial pressure is uniform 0.0 mmHg.
- property outputs are inlet.dat, outlet.dat, whole.dat with period 100.

### Inlet/outlet BC block content in input_PP.xml
The inlet and outlet blocks come from voxelizer file iolets_block_inputxml_PP.txt.

With the current script setting BCExtensions=["PP"], the generated file is input_PP.xml and the iolet conditions are pressure cosine blocks from the PP template.

Important implication:
- The script generates velocity and WK weight files even though input_PP.xml itself uses pressure-cosine iolet conditions by default.
- Those weight files are used when you switch XML BCs to the corresponding file-weighted velocity or WK implementations.

### Parameters you can safely edit before simulation
- simulation/steps (required)
- initial pressure
- output periods and output file names
- BC amplitudes/means/periods/phases in inlet/outlet condition blocks

Advanced edits (geometry consistency sensitive):
- inlet and outlet positions
- inlet and outlet normals
- radii and areas

## Boundary conditions implemented in solver code

### Inflow-related classes
| Class | Type | Uses weight file |
|---|---|---|
| InOutLetParabolicVelocity | Velocity inlet | No |
| InOutLetFileVelocity | Velocity inlet from time file | Optional yes, via file.weights.txt when compiled with HEMELB_USE_VELOCITY_WEIGHTS_FILE |
| InOutLetWomersleyVelocity | Velocity inlet | No |
| InOutLetWomersleyElasticVelocity | Velocity inlet | No |
| InOutLetTurbulentVelocity | Velocity inlet | No |

### Outflow-related classes
| Class | Type | Uses weight file |
|---|---|---|
| InOutLetWK | Windkessel outlet | No |
| InOutLetFileWK | Windkessel outlet | Yes, reads WK weights file |

### Pressure classes used on iolets
| Class | Type | Uses weight file |
|---|---|---|
| InOutLetCosine | Pressure cosine | No |
| InOutLetFile | Pressure from file | No |
